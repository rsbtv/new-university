1. Основы документирования на Doxygen

1.1. Основные принципы и подходы.

1.1.1. Документация кода в Doxygen осуществляется при помощи документирующего блока. При этом допускается его размещения только перед объявлением или определением класса, члена класса, функции, пространства имён и т.д.;

1.1.2. Структурно, любой документирующий блок является комментарием, просто оформленным специальным образом. Сразу отметим, что, вообще, всего существует два основных типа документирующих блоков: многострочный блок и однострочный блок.

1.1.3. Разница между ними чуть более сильная, чем между однострочным и многострочным комментарием. Дело в том, что текст, написанный в однострочном блоке, относится к краткому описанию документируемого элемента (сродни заголовку), а текст, написанный в многострочном блоке, относится к подробному описанию. Про эту разницу не следует забывать.

1.2. Многострочный блок.

1.2.1. Любой блок – это комментарий, оформленный специальным образом. Допускается использование следующего вида:

/**

 * ... первая строчка ...

 * ... вторая строчка ...

 */

1.2.2. При этом звездочки обязательно ставить на каждой строке.

1.2.3. Текст, написанный в таком комментарии, относится к подробному описанию. Для указания краткого описания должна быть использована команда @brief. Указанный после команды текст, вплоть до конца параграфа будет относится к краткому описания, и для отделения подробного описания и краткого описания используется пустая строка.

/**

 * @brief.Краткое описание

 * и его продолжение

 *

 * Подробное описание.

 */

1.3. Однострочный блок.

1.3.1. Для описания однострочного блока необходимо использовать специальный комментарий в C++ стиле:

/// Краткое описание

1.3.2. Для указания подробного описания в однострочном документирующем блоке может быть использована команда @details:

/// @details Подробное описание

1.3.3. Документирующие блоки, следующие друг за другом, объединяются в один (причем вне зависимости от используемого стиля и того, являются они многострочными или однострочными). Например, следующие два способа документирования дадут один и тот же результат:

/// @brief Краткое описание

/// @details Подробное описание

 

///Краткое описание

/**

 * Подробное описание

*/

2. Документирование основных элементов исходного кода

2.1. Введение общих обозначений для примеров.

2.1.1. Далее будут использоваться обозначения при описании аргументов команды, когда будет приводиться её общий формат, эти обозначения представлены в Таблица 4.

Таблица 2

Обозначение

Значение

<...>

Угловые скобки показывают, что аргумент представляет собой одно слово

(...)

Круглые скобки показывают, что аргументом является весь текст вплоть до конца строки, на которой размещена команда

{...}

Фигурные скобки показывают, что аргументом является весь текст вплоть до следующего параграфа. Параграфы разделяются пустой строкой

 

2.2. Документирование функций и методов.

2.2.1. При документировании функций и методов необходимо указать входные параметры, возвращаемое функцией значение, а также возможные исключения. Рассмотрим последовательно соответствующие команды.

2.2.2. Для указания параметров необходимо использовать команду @param для каждого из параметров функции, при этом синтаксис команды имеет следующий вид:

@param [<направление>] <имя_параметра> {описание_параметра}

 

 

2.2.3. Рассмотрим значение компонентов команды:

а)       Имя параметра – это имя, под которым данный параметр известен в документируемом коде;

б)      Описание параметра представляет собой простое текстовое описание используемого параметра;

в)       Направление – это опциональный атрибут, который показывает назначение параметра и может иметь три значения "[in]", "[out]", "[in,out]";

ПРИМЕР.

/**

 * Копирует содержимое из исходной области памяти в целевую область

 * @param[out] dest Целевая область памяти

 * @param[in] src Исходная область памяти

 * @param[in] n Количество байтов, которые необходимо скопировать

*/

void memcpy(void *dest, const void *src, size_t n);

2.2.4. Для описание возвращаемого значения используется команда @return Её синтаксис имеет следующий вид:

@return {описание_возвращаемого_значения}

ПРИМЕР.

/**

 * Находит сумму двух чисел

 * @param a,b Складываемые числа

 * @return Сумму двух чисел, переданных в качестве аргументов

 */

double sum(const double a, const double b);

 

2.2.5. Для указания исключения используется команда @throw которая имеет следующий формат:

\throw <объект-исключение> {описание}

ПРИМЕР:

@throw std::bad_alloc При возникновения ошибки при выделении памяти

2.3. Документирование классов.

2.3.1. Классы также могут быть документированы просто предварением их документирующим блоком. При этом огромное количество информации Doxygen получает автоматически, учитывая синтаксис языка, поэтому задача документирования классов значительно упрощается. Так при документировании Doxygen автоматические определяет методы и члены класса, уровни доступа к функциям, дружественные функции и т.п.

2.4. Документирование файлов.

2.4.1. Для документирования файлов используется директива @file. После в том же блоке комментария с помощью директивы @brief добавляется краткое описание файла, после этого может так же быть добавлено подробное описание файла.

ПРИМЕР:

/**

 * @file

 * @brief This file contain function for work with modbus.

 *

 * This is full description of the file.

 */

2.5. Документирование перечислений.

2.5.1. Документирование перечислений не сильно отличается от документирования других элементов. Рассмотрим пример, в котором иллюстрируется то, как можно удобно документировать их:

/// Набор возможных состояний объекта

enum States {

   Disabled, ///< Указывает, что элемент недоступен для использования

   Undefined, ///< Указывает, что состояние элемента неопределенно

   Enabled, ///< Указывает, что элемент доступен для использования

}

То есть описание состояний указывается, собственно, после них самих при помощи краткого или подробного описания (в данном случае роли это не играет).

2.6. Блок кода внутри документации.

2.6.1. Зачастую внутри пояснения к документации необходимо для примера добавить код, например для иллюстрации работы функции.

2.6.2. Делать это необходимо с помощью команды \code и \endcode, которые применяются следующим образом:

@code [ {<расширение>}]

     ...

@endcode

2.6.3. Используемый язык определяется автоматически в зависимости от расширения файла, в котором располагается документирующий блок, однако в случае, если такое поведение не соответствует ожиданиям расширение можно указать явно.

ПРИМЕР:

/**

 * @brief Алгоритм Евклида

 * @param a,b Два числа, чей наибольший делитель мы хотим найти

 *

 * Данная функция реализует алгоритм Евклида, при помощи которого

 * находится наибольшее общее кратное у двух чисел.

 *

 * Код функции выглядит следующим образом:

 * @code

 * int gcd(int a, int b) {

 *    int r;

 *    while (b) {

 *       r = a % b;

 *       a = b;

 *       b = r;

 *    }

 *    return r;

 * }

 * @endcode

*/

int gcd(int a, int b);

2.7. Записи TODO.

2.7.1. Для создания записи TODO необходимо добавить блок следующего вида:

/// @todo TODO (текст TODO)

2.7.2. Блок TODO так же может входить в многострочный блок описания класса, функции и т.д. В этом случае он будет иметь следующий вид:

/**

 * @brief {краткое описание блока}

 *

 * {Подробное описание блока}

 * @todo TODO (описание записи TODO)

 */

2.7.3. Создание многострочной записи TODO не допускается, так как среда редактора не будет отображать вторую строчку записи.

3. Модули

3.1. Создание модуля

3.1.1. Для объявления модуля рекомендуется использовать команду @defgroup, которую необходимо заключить в документирующий блок:

@defgroup <идентификатор> (заголовок модуля)

3.1.2. Идентификатор модуля представляет собой уникальное слово, написанное на латинице, который впоследствии будет использован для обращения к данному модулю; заголовок модуля – это имя которое будет отображаться в документации.

3.1.3. При описании модуля можно дополнить его кратким и подробным описанием, что позволяет раскрыть назначение того или иного модуля, например:

/**

 * @defgroup mazeGeneration Генерация лабиринтов

 * @brief Данный модуль, предназначен для генерации лабиринтов.

 * На данный момент он поддерживает следующие алгоритмы генерации 

 * лабиринтов: Eller's algorithm, randomized Kruskal's algorithm,

 * cellular automaton algorithm, randomized Prim's algorithm.

*/

3.2. Размещение документируемого элемента в модуле.

3.2.1. Для того, чтобы отнести тот или иной документируемый элемент в модуль, существуют два подхода.

3.2.2. Первый подход – это использование команды @ingroup:

@ingroup <идентификатор> (заголовок модуля)

Его недостатком является то, что данную команду надо добавлять в документирующие блоки каждого элемента исходного кода, поскольку их в рамках одного модуля может быть достаточно много.

3.2.3. Второй подход состоит в использовании команд начала и конца группы: @{ и @}. Следует отметить, что они используются наряду с командами @defgroup, @addtogroup и @weakgroup.

ПРИМЕР:

/**

 * @defgroup <идентификатор> (заголовок модуля)

 * @{

*/

  документируемые_элементы

/// @}

Однако, модуль должен определяться один раз, причём это объявление будет только в одном файле, а часто бывает так, что элементы одного модуля разнесены по разным файлам и потому возникает необходимость использования команды @addtogroup, которая не переопределяет группу, а добавляет к ней тот или иной элемент:

/**

 * @addtogroup <идентификатор> [(заголовок модуля)]

 * @{

*/

   документируемые_элементы

/// @}

Название модуля указывать необязательно. Дело в том, что данная команда может быть использована как аналог команды @defgroup, и если соответствующий модуль не был определена, то она будет создана с соответствующим названием и идентификатором.

3.2.4. Команда @weakgroup аналогична команде @addtogroup, отличие заключается в том, что она просто имеет меньший приоритет по сравнению с ней в случае если возникают конфликты, связанные с назначение одного и того же элемента к разным модулям.

3.3. Создание подмодуля.

3.3.1. Для создания подмодуля достаточно при его определении отнести его к тому или иному подмодулю, подобно любому другому документируемому элементу.

ПРИМЕР:

/**

 * @defgroup main_module Главный модуль

*/

 

/**

 * @defgroup second_module Вложенный модуль

 * @ingroup main_module

 */

4. Требования к документированию кода

4.1. Общие требования к документированию.

4.1.1. Документирующие блоки всегда добавляются только в заголовочном файле *.h, исключение могут составлять только документирование констант, определенных в *.cpp или *.c файле.

4.1.2. Написание всех комментариев, как в документируемых блоках, так и во всех других местах должно производиться на английском языке.

4.2. Документирование подмодулей, библиотек и программ.

4.2.1. В корневой директории каждого подмодуля, библиотеки или программы должен быть создан файл, название которого соответствует названию подмодуля, библиотеки или программы соответственно, расширение файла должно быть *.dox. В данном файле определяется положение подмодуля, библиотеки или программы в структуре документации, определяется отдельная группа, и приводится краткое и подробное описание данной группы. Положение в структуре документации должно соответствовать расположению проекта на git сервере.

4.2.2. Положение в структуре документации определяется с помощью директивы:

/**

* @addtogroup  <идентификатор> [(заголовок модуля)]

 * @{

 *

 * @}

 */

4.2.3. Идентификатор должен соответствовать названию папки в файловой структуре git сервера. Если название папки содержит точку (.) , тогда в идентификаторе точку необходимо заменить на нижнее подчеркивание (_).

4.2.4. Заголовок модуля остается пустым, за исключением случаев приведенных ниже.

4.2.5. Заголовок модуля заполняется таким же, как и идентификатор, если название идентификатора начинается с цифры, данное правило применяется для программ, группа которых начинается с номера, например 15T555.

4.2.6. Заголовок модуля заполняется отличным от идентификатора, если в идентификаторе была произведена замена точки на нижнее подчеркивание, в соответствии с пунктом 4.1.3, тогда в заголовке модуля должна быть использована точка.

ПРИМЕР:

Если модуль расположен по пути /Programs/14T161.4301/ тогда его структура в документации должна определяться следующим образом:

/**

 * @addtogroup Programs

 * @{

 * @addtogroup 14T161_4301 14T161.4301

 * @{

 * @defgroup <идентификатор>

 *

 * @}

 * @}

 */

4.2.7. Определение модуля должно осуществляться через директиву @defgroup и должно содержать краткое описание модуля через директиву @brief и подробное описание. Если для работы модуля необходимо подключение других подмодулей, тогда в подробном описании должен быть приведен список данных модулей в директиве @attention. Данный блок должен идти непосредственно после директивы краткого описания @brief и перед подробным описанием. После каждого элемента списка должна ставиться точка-запятая (;), а после последнего ставится точка (.). Название любых модулей указываемых в описание должно осуществляться через директиву @ref. Таким образом, требуемое описание модуля должно иметь следующий вид:

/**

* @defgroup CanOpenBase

 * @brief Base module CanOpen bus.

 * @attention Plug-in required:

 *    - @ref CanBaseDataModel submodule;

 *    - @ref CanBase submodule.

 *

 * Submodule using as a base module for CanOpen submodules.

 * This submodule must be used when user need write or read from

 * CanOpen bus.

 */

4.2.8. После подробного описания модуля должны идти разделы, описывающие подключение данного модуля к проекту. В Таблица 3 указаны возможные секции, подсекции и их описание. Для добавления обязательны секции помеченные звездочкой (*). Добавление секций и подсекций должно идти в том же порядке, что и в таблице.

4.3. Документирование классов, входящих в состав модулей.

4.3.1. Документирование классов, входящих в состав модулей, осуществляется в соответствии с пунктом 2.3, только после полного описания необходимо добавить директиву @ingroup (в соответствии с пунктом 3.2.2) для установки принадлежности текущего класса.

4.3.2. В классе принадлежность к модулю определяется только у самого класса, у методов, сигналов, переменных, перечислений и т.д. принадлежность к модулю не устанавливается.

4.4. Документирование файлов, входящих в состав модулей.

4.4.1. Если файл описывает класс, тогда документировать данный файл запрещается, вместо этого документируется сам класс в соответствии с пунктом 4.3.

4.4.2.  Документирование файлов, входящих в состав модулей, осуществляется в соответствии с пунктом 2.4, только после полного описания необходимо добавить директиву @ingroup (в соответствии с пунктом 3.2.2) для установки принадлежности текущего файла.

4.4.3. В файле принадлежность к модулю определяется только у самого файла, у функций, переменных, перечислений и т.д. принадлежность к модулю не устанавливается.
