1. Соглашения об именовании

1.1. Общие соглашения об именовании

1.1.1. Имена, представляющие типы (встроенные и пользовательские, напр., структуры и классы), должны быть обязательно написаны в смешанном регистре, начиная с верхнего регистра. В C++ нижнее подчеркивание в наименованиях не допускается.

Хорошо

Line, SavingsAccount

 

ПОЧЕМУ. Общая практика в сообществе разработчиков C и C++.

 

1.1.2. Имена переменных должны быть записаны в смешанном регистре, начиная с нижнего.

Хорошо

line, savingsAccount

 

ПОЧЕМУ. Общая практика в сообществе разработчиков C++. Позволяет легко отличать переменные от типов, предотвращает потенциальные коллизии имён, например: Line line;

 

1.1.3. Названия методов и функций должны содержать глаголы, быть записанными в смешанном регистре и начинаться с нижнего регистра.

Хорошо

getName(), computeTotalWidth()

 

ПОЧЕМУ. Совпадает с правилом для переменных, но отличие между ними состоит в их специфических формах.

 

1.1.4. Названия пользовательских пространств имён следует записывать в смешанном регистре, начиная с верхнего регистра. В C допускается использование нижнего подчеркивания. В C++ использование нижнего подчеркивания не допускается.

Хорошо

MyClass::analyzer;

BaseClass::OneMoreClass::geometry;

 

ПОЧЕМУ. Общая практика в сообществе разработчиков C и C++.

 

1.1.5. Имена типов в шаблонах возможно называть одной заглавной буквой, если назначение параметра шаблона очевидно. Если шаблон имеет более одного параметра, каждый параметр иметь название, отражающее его назначение. В этом случае название должно быть записано в смешанном регистре, начиная с верхнего регистра.

Хорошо

template<class T> ...

template<class Database, class Stack> ...

 

ПОЧЕМУ. Общая практика в сообществе разработчиков C и C++. Позволяет выделить имена шаблонов среди других используемых имён.

 

1.1.6. Аббревиатуры и сокращения в именах должны записываться в нижнем регистре.

Хорошо

Плохо

exportHtmlSource();

exportHTMLSource();

openDvdPlayer();

openDVDPlayer();

 

ПОЧЕМУ. Использование верхнего регистра может привести к конфликту имён, описанному выше. Иначе переменные бы имели имена dVD, hTML и т. д., что не является удобочитаемым, слово, следующее за аббревиатурой, не выделяется так, как следовало бы.

 

1.1.7. Глобальные переменные всегда следует использовать с оператором разрешения области видимости (::).

Хорошо

::mainWindow.open();

::applicationContext.getName()

 

ПОЧЕМУ. Следует избегать использования глобальных переменных.

 

1.1.8. Членам класса с модификатором private следует присваивать префиксное подчёркивание.

Хорошо

class SomeClass

{

 

private:
    int _length;

}

 

ПОЧЕМУ. Не считая имени и типа, область видимости — наиболее важное свойство переменной. Явное указание модификатора доступа в виде подчёркивания избавляет от путаницы между членами класса и локальными переменными.

 

1.1.9. Настраиваемым переменным, принадлежащим пользовательским типам данных, следует давать то же имя, что и у их типа.

Хорошо

Плохо

void setTopic(Topic* topic)

void setTopic(Topic* value)

void setTopic(Topic* aTopic)

void setTopic(Topic* t)

void connect(Database* database)

void connect(Database* db)

void connect (Database* oracleDB)

 

ПОЧЕМУ. Сокращайте сложность путём уменьшения числа используемых терминов и имён. Также упрощает распознавание типа просто по имени переменной. Данное правило не относится к переменным встроенных типов.

 

1.1.10. Все имена следует записывать по-английски.

Хорошо

Плохо

fileName

imyaFayla

 

ПОЧЕМУ. Английский наиболее предпочтителен для интернациональной разработки.

 

1.1.11. Переменные, имеющие большую область видимости, следует называть длинными именами, имеющие небольшую область видимости — короткими.

 

ПОЧЕМУ. Имена временных переменных, использующихся для хранения временных значений или индексов, лучше всего делать короткими. Программист, читающий такие переменные, должен иметь возможность предположить, что их значения не используются за пределами нескольких строк кода. Обычно это переменные i, j, k, l, m, n (для целых), а также c и d (для символов).

 

1.1.12. Имена объектов не указываются явно, следует избегать указания названий объектов в именах методов.

Хорошо

Плохо

line.getLength();

line.getLineLength();

 

ПОЧЕМУ. Второй вариант смотрится вполне естественно в объявлении класса, но совершенно избыточен при использовании, как это и показано в примере.

1.2. Особые правила именования

1.2.1. Функция, предоставляющая доступ к чтению атрибута, должна быть названа аналогично имени атрибута, без нижнего подчеркивания, в смешанном регистре. Слово set должно быть использовано везде, где осуществляется прямая перезапись значения атрибута.

Хорошо

employee.name();

employee.setName(name);

matrix.element(2, 4);

matrix.setElement(2, 4, value);

 

ПОЧЕМУ. Общая практика в сообществе разработчиков C и C++. В Java это соглашение стало более-менее стандартным.

 

1.2.2. Слово compute может быть использовано в методах, вычисляющих что-либо.

Хорошо

valueSet->computeAverage();

matrix->computeInverse();

 

ПОЧЕМУ. Дайте читающему сразу понять, что это времязатратная операция.

 

1.2.3. Слово find может быть использовано в методах, осуществляющих какой-либо поиск.

Хорошо

vertex.findNearestVertex();

matrix.findMinElement();

 

ПОЧЕМУ. Дайте читающему сразу понять, что это простой метод поиска, не требующий больших вычислений.

 

1.2.4. Слово initialize либо init может быть использовано там, где объект или сущность инициализируется.

Хорошо

printer.initializeFontSet();

matrix.init();

 

ПОЧЕМУ. Следует отдавать предпочтение американскому варианту initialize, нежели британскому initialise.

 

1.2.5. Переменным, представляющим GUI, следует давать суффикс, соответствующий имени типа компонента.

Хорошо

mainWindow, propertiesDialog, widthScale, loginText,
leftScrollbar, mainForm, fileMenu, minLabel, exitButton, yesToggle и т. д.

 

ПОЧЕМУ. Улучшает читаемость, поскольку имя даёт пользователю прямую подсказку о типе переменной и, следовательно, ресурсах объектов.

 

1.2.6. Множественное число следует использовать для представления наборов (коллекций) объектов.

Хорошо

vector<Point> points;

int values[];

 

ПОЧЕМУ. Улучшает читаемость, поскольку имя даёт пользователю прямую подсказку о типе переменной и операциях, которые могут быть применены к этим элементам.

 

1.2.7. Для представления числа объектов следует использовать постфикс Number, название формируется по шаблону <objectName>Number.

Хорошо

pointsNumber, linesNumber

 

1.2.8. Переменным-итераторам следует давать имена i, j, k и т. д.

 

Хорошо

for (int i = 0; i < nTables); i++) {
    …

}

for (vector<MyClass>::iterator i = list.begin();
    i!= list.end();
    i++) {
    Element element = *i;
    …

}

 

ПОЧЕМУ. Обозначение взято из математики, где оно является установившимся соглашением для обозначения итераторов.

Переменные с именами j, k и т. д. рекомендуется использовать только во вложенных циклах.

 

1.2.9. Префикс is следует использовать только для булевых (логических) переменных и методов.

Хорошо

isSet, isVisible, isFinished, isFound, isOpen

 

ПОЧЕМУ. Общая практика в сообществе разработчиков C и C++, иногда используемая и в Java. Использование этого префикса избавляет от таких имён, как status или flag.

В некоторых ситуациях префикс is лучше заменить на другой: has, can или should:

 

Хорошо

bool hasLicense();

bool canEvaluate();

bool shouldSort();

 

1.2.10. Симметричные имена должны использоваться для соответствующих операций.

Хорошо

get/set, add/remove, create/destroy, start/stop, insert/delete,
increment/decrement, old/new, begin/end, first/last, up/down, min/max,
next/previous, old/new, open/close, show/hide, suspend/resume, и т.д.

 

ПОЧЕМУ. Уменьшайте сложность за счёт симметрии.

 

1.2.11. Следует избегать сокращений в именах.

Хорошо

Плохо

computeAverage();

compAvg();

 

ПОЧЕМУ. Рассмотрим два вида слов. Первые — обычные слова, перечисляемые в словарях, которые нельзя сокращать. Никогда не сокращайте:

- cmd вместо command;

- cp вместо copy;

- pt вместо point;

- comp вместо compute.

Второй вид — слова, специфичные для какой-либо области, которые известны по своему сокращению/аббревиатуре. Их следует записывать сокращённо. Никогда не пишите:

- HypertextMarkupLanguage вместо html;

- CentralProcessingUnit вместо cpu;

- PriceEarningRatio вместо pe  и т. д.

 

1.2.12. Следует избегать дополнительного именования указателей.

Хорошо

Плохо

Line* line;

Line* pLine;

Line* linePtr;

 

ПОЧЕМУ. Множество переменных в C/C++ являются указателями. Только в том случае, когда тип объекта в языке C++ особенно важен, имя должно отражать его.

 

1.2.13. Нельзя давать булевым (логическим) переменным имена, содержащие отрицание.

 

 

Хорошо

Плохо

bool isError;

isNoError

bool isFound;

isNotFound

 

ПОЧЕМУ. Проблема возникает, когда такое имя используется в конъюнкции с оператором логического отрицания, что влечёт двойное отрицание. Результат не обязательно будет отрицанием !isNotFound.

 

1.2.14. При объявлении перечислений enum константы могут иметь префикс — общее имя типа. В случае использования типа enum class или enum structure префикс в имени константы является избыточным.

Хорошо

enum Color {
 COLOR_RED,
 COLOR_GREEN,

};

enum class Color {
RED,
GREEN,

};

 

ПОЧЕМУ. Префикс элементов перечисления enum даёт дополнительную информацию о том, где находится объявление, какие константы описаны в одном перечислении, а также какую концепцию являют собой константы.

В случае использования enum class или enum structure к константам обращаются по их общему типу: Color::RED, Airline::AIR_FRANCE и т. д.

Обратите внимание, что имя перечисления обычно записано в единственном числе, например: enum Color {...}. Имя во множественном числе хорошо выглядит при объявлении, но не очень хорошо подходит для практического использования.

 

1.2.15. Классам исключений следует присваивать суффикс Exception.

Хорошо

class AccessException

{
  …

}

 

ПОЧЕМУ. Классы исключений в действительности не являются частью архитектуры программ, и такое именование отделяет их от других классов.

 

1.2.16.  Функциям (методам, возвращающим какие-либо значения) следует давать имена в зависимости от того, что они возвращают, а процедурам — в зависимости от того, что они выполняют (методы void).

 

ПОЧЕМУ. Улучшайте читаемость. Такое именование даёт понять, что метод делает, а что нет, а также избавляет код от потенциальных побочных эффектов.

 

2. Файлы

2.1. Файлы исходных кодов

2.1.1. Заголовочным файлам C++ следует давать расширение .h (предпочтительно) либо .hpp. Файлы исходных кодов могут иметь расширения .C, .cc либо .cpp.

Хорошо

MyClass.cpp, MyClass.h

 

ПОЧЕМУ. Это расширения, одобряемые стандартом C++.

 

2.1.2. Класс следует объявлять в заголовочном файле и определять (реализовывать) в файле исходного кода, имена файлов совпадают с именем класса.

Хорошо

MyClass.h, MyClass.cpp

 

ПОЧЕМУ. Облегчает поиск связанных с классом файлов. Очевидное исключение — шаблонные классы, которые должны быть объявлены и определены в заголовочном файле.

 

2.1.3. Все определения должны находиться в файлах исходного кода.

 

Хорошо

Плохо

MyClass.h

MyClass.cpp

class MyClass

{

public:
int getValue ()
{
    return _value;
}

private:
  int _value;

};

class MyClass

{

public:
int getValue ();
...

private:
int value_;

};

int MyClass::
 getValue()

{
 return value_;

}

 

ПОЧЕМУ. Заголовочные файлы объявляют интерфейс, файлы исходного кода его реализовывают. Если программисту необходимо найти реализацию, он должен быть уверен, что найдёт её именно в файле исходного кода, кроме того, таким образом сокращается время повторных компиляций.

 

2.1.4. Содержимое файлов не должно превышать 80 колонок.

 

ПОЧЕМУ. 80 колонок — широко распространённое разрешение для редакторов, эмуляторов терминалов, принтеров и отладчиков; файлы передаются между различными людьми, поэтому нужно придерживаться этих ограничений. Уместная разбивка строк улучшает читаемость при совместной работе над исходным кодом.

 

2.1.5. Нельзя использовать специальные символы (например, TAB) и разрывы страниц.

 

ПОЧЕМУ. Такие символы вызывают ряд проблем, связанных с редакторами, эмуляторами терминалов и отладчиками, используемыми в программах для совместной разработки и кроссплатформенных средах.

 

2.1.6. Незавершённость разбитых строк должна быть очевидна.

Хорошо

totalSum = a
+ b + c
+ d + e;

mainBoolVar = boolVar1
&& boolVar2
|| boolVar3;

fun (param1, param2,
param3);

functionWithVeryLongName(
longParameter1,
longParameter2,
longParameter3);

for (int tableNo = 0; 
tableNo < nTables;
tableNo += tableStep)

{
...

}

setText ("Long"
"line"
"split"
"into"
"many"
"parts.");

MyClass::MyClass()

    : parameter1{}

    , parameter2{}

    , parameter3{}

 

 

ПОЧЕМУ. Разбивка строк появляется, когда ограничение на 80 колонок, описанное выше, нарушается. Примеры выше показывают общие принципы.

В общем случае:

- разрыв после запятой, кроме инициализаций внутри конструктора;

- разрыв до оператора;

- выравнивание новой строки с началом выражения на предыдущей строке.

2.2. Директивы

2.2.1. Заголовочные файлы должны содержать защиту от вложенного включения.

Хорошо

#ifndef COM_COMPANY_MODULE_CLASSNAME_H

#define COM_COMPANY_MODULE_CLASSNAME_H

  :

#endif // COM_COMPANY_MODULE_CLASSNAME_H

#pragma once

 

ПОЧЕМУ. Конструкция позволяет избегать ошибок компиляции. Это соглашение позволяет увидеть положение файла в структуре проекта и предотвращает конфликты имён.

 

2.2.2. Директивы включения следует сортировать (по месту в иерархии системы, ниже уровень — выше позиция) и группировать. Оставляйте пустую строку между группами.

Хорошо

#include <fstream>

#include <iomanip>

 

#include <qt/qbutton.h>

#include <qt/qtextfield.h>

 

#include "com/company/ui/PropertiesDialog.h"

#include "com/company/ui/MainWindow.h"

 

ПОЧЕМУ. Пути включения не должны быть абсолютными. Вместо этого следует использовать директивы компилятора.

 

2.2.3. Директивы включения должны располагаться только в начале файла.

 

ПОЧЕМУ. Общая практика. Избегайте нежелательных побочных эффектов, которые может вызвать «скрытое» включение где-то в середине файла исходного кода.

 

2.2.4. Необходимо избегать включения заголовочных файлов, если возможно объявление класса.

Хорошо

Нежелательно

class MyClass;

#include <myclass.h>

 

ПОЧЕМУ. Если необходимые атрибуты класса передаются по ссылке, объявление класса поддерживает такую же функциональность, как включение соответствующего заголовочного класса, но ускоряет компиляцию.

 

2.2.5. Требуется избегать директивы #DEFINE при возможности.

 

ПОЧЕМУ. Содержимое макроса предварительно не проверяется компилятором и выполняется препроцессором без проверки. К примеру, в разных макросах могут использоваться одноименные переменные, и т.д.

 

3. Выражения

3.1. Типы

3.1.1. Локальные типы, используемые в одном файле, должны быть объявлены только в нём.

 

ПОЧЕМУ. Улучшает инкапсуляцию информации.

 

3.1.2. Приведение типов должно быть явным. Никогда не полагайтесь на неявное приведение типов. Используйте static_cast, const_cast, dynamic_cast в C и нотацию (<some type>) в C++.

Хорошо

Плохо

floatValue =

static_cast<float>(intValue);

floatValue = intValue;

 

ПОЧЕМУ. Этим программист показывает, что ему известно о различии типов, что смешение сделано намеренно.

3.2. Переменные

3.2.1. Следует инициализировать переменные в месте их объявления.

 

ПОЧЕМУ. Это даёт гарантию, что переменные пригодны для использования в любой момент времени. Но иногда нет возможности осуществить это:

  int x, y, z;

  getCenter(&x, &y, &z);

В этих случаях лучше оставить переменные неинициализированными, чем присваивать им какие-либо значения.

 

3.2.2. Переменные никогда не должны иметь двойной смысл.

 

ПОЧЕМУ. Улучшайте читаемость, убеждаясь, что все представленные концепции не предполагают разночтений. Сокращайте возможность ошибки из-за побочных эффектов.

 

3.2.3. Следует избегать использования глобальных переменных.

 

ПОЧЕМУ. Не существует причины использовать глобальные переменные в C++. То же касается глобальных функций и (статических) переменных, область видимости которых — весь файл.

 

3.2.4. Нельзя объявлять переменные класса как public.

 

ПОЧЕМУ. Эти переменные нарушают принципы сокрытия информации и инкапсуляции. Вместо этого используйте переменные с модификатором private и соответствующие функции доступа. Исключение — класс без поведения, практически структура данных (эквивалент структур языка C). В этом случае нет смысла скрывать эти переменные.

 

3.2.5. Классы необходимо использовать для инкапсуляции связанных между собой параметров. Для не связанных между собой параметров следует использовать структуры.

 

3.2.6. Символ указателя или ссылки в языке C++ следует ставить сразу после имени типа, а не с именем переменной.

 

 

Хорошо

Плохо

float* x; int& y;

float *x; int &y;

 

ПОЧЕМУ. То, что переменная — указатель или ссылка, относится скорее к её типу, а не к имени. Программисты на C часто используют другой подход, но в C++ лучше придерживаться этой рекомендации.

 

3.2.7. Следует избегать неявного сравнения небулевых переменных и указателей с нулём.

Хорошо

Плохо

if (nLines != 0)

if (nLines)

if (value != 0.0)

if (value)

 

ПОЧЕМУ. Стандарт C++ не гарантирует, что значения переменных разных типов, эквивалентные нулю, будут представлены как бинарный 0. Также при явном сравнении видно сравниваемый тип.

Также указатели не следует неявно сравнивать с нулём. Следует использовать подходящий эквивалент нуля для разных типов данных в соответствующем языке.

Хорошо

Плохо

if (line == NULL) в C

if (line)

if (line == nullptr) в C++

 

3.2.8. Переменные следует объявлять в как можно меньшей области видимости.

 

ПОЧЕМУ. Это упрощает контроль над действием переменной и сторонними эффектами.

3.3. Циклы

3.3.1. Нельзя включать в конструкцию for() выражения, не относящиеся к управлению циклом.

Хорошо

Плохо

sum = 0;

for (i = 0; i < 100; i++)

{
sum += value[i];

}

for (i = 0, sum = 0;
i < 100;
i++)
sum += value[i];

 

ПОЧЕМУ. Улучшайте поддержку и читаемость. Строго разделяйте контроль над циклом и то, что в нём содержится.

 

3.3.2. Переменные, относящиеся к циклу, следует инициализировать непосредственно перед ним.

 

3.3.3. Необходимо избегать циклов do-while.

 

ПОЧЕМУ. Такие циклы хуже читаемы, поскольку условие описано после тела. Читающему придётся просмотреть весь цикл, чтобы понять его работу.

Циклы do-while вообще не являются острой необходимостью. Любой такой цикл может быть заменён на цикл while или for. Меньшее число используемых конструкций улучшает читаемость.

 

3.3.4. Следует избегать использования break и continue в циклах.

 

ПОЧЕМУ. Такие выражения следует использовать только тогда, когда они повышают читаемость.

 

3.3.5. Для бесконечных циклов следует использовать форму for(;;).

 

Хорошо

Плохо

for (;;)

{
    …

}

while (true)

{
    …

}

while (1)

{
    …

}

 

ПОЧЕМУ. Цикл while(true) в общем случае требует присоединения дополнительных библиотек.

3.4. Условные выражения

3.4.1. Условие следует размещать в отдельной строке.

Хорошо

Плохо

if (isDone)

{
    doCleanup();

}

if (isDone) doCleanup();

 

ПОЧЕМУ. Улучшает читаемость кода.

 

3.5. Разное

3.5.1. Следует избегать «магических» чисел в коде. Числа, отличные от 0 или 1, следует объявлять как именованные константы.

 

ПОЧЕМУ. Если число само по себе не имеет очевидного значения, читаемость улучшается путём введения именованной константы.

 

3.5.2. Константы с плавающей точкой следует записывать с десятичной точкой и с указанием по крайней мере одной цифры после запятой.

Хорошо

Плохо

double total = 0.0;

double total = 0;

double speed = 3.0e8;

double speed = 3e8;

double sum;

sum = (a + b) * 10.0;

double sum;

sum = (a + b) * 10

 

ПОЧЕМУ. Это подчёркивает различные подходы при работе с целыми числами и числами с плавающей точкой. С точки зрения математики, эти две модели совершенно различны и не совместимы.

А также (как это показано в последнем примере выше) делается акцент на типе переменной (sum) в том месте, где это не является очевидным.

 

3.5.3. Константы с плавающей точкой следует всегда записывать, по крайней мере, с одной цифрой до десятичной точки.

Хорошо

Плохо

double total = 0.5;

double total = .5;

 

ПОЧЕМУ. Система чисел и выражений в C++ заимствована из математики, и следует придерживаться традиционных форм записи, где это возможно. Помимо прочего, 0.5 — более читаемо, чем .5 (первый вариант никак не спутать с числом 5).

 

3.5.4. У функций нужно обязательно указывать тип возвращаемого значения.

Хорошо

Плохо

int getValue();

getValue();

 

ПОЧЕМУ. Если это не указано явно, C++ считает, что возвращаемое значение имеет тип int.

 

3.5.5. Строго запрещено использовать goto.

 

ПОЧЕМУ. Этот оператор нарушает принципы структурного программирования.

 

3.5.6. Следует использовать NULL вместо 0 в C, nullptr вместо NULL в C++.

 

ПОЧЕМУ. NULL является частью стандартной библиотеки C и устарело в C++.

4. Оформление и комментарии

4.1. Отступы

4.1.1. Основной отступ следует делать в четыре пробела.

Хорошо

for (i = 0; i < elementsNumber; i++)

{
a[i] = 0;

}

 

ПОЧЕМУ. Отступ в один пробел достаточно мал, чтобы отражать логическую структуру кода. Отступ более 4 пробелов делает глубоко вложенный код нечитаемым и увеличивает вероятность того, что строки придётся разбивать. Широко распространены варианты в 2, 3 или 4 пробела; причём 2 и 4 — более широко.

 

4.1.2. Функции, классов и методов следует оформлять с отступами в 4 пробела тела функции, класса либо метода. Для скобки отступы не делаются.

Хорошо

Плохо

while (!done) {
doSomething();
done = moreToDo();

}

while (!done)
{
    doSomething();
    done = moreToDo();
}

while (!done)

{
doSomething();
done = moreToDo();

}

 

ПОЧЕМУ. Лишние отступы мешают ясному отображению логической структуры кода.

Исключением является составной оператор switch-case, в котором case не выделяется отступами, как и фигурная скобка.

 

4.1.3. Разделы в объявлениях классов не выделяются отступами. Объявления методов и переменных класса выделяются отступами в 4 пробела.

Хорошо

class MyClass()

{

public:

    somePublicFun();

 

private:

    int _privateParam;

 

private:

    somePrivateFun();

};

 

ПОЧЕМУ. Разделы класса с разными правами доступа проще находить.

 

4.1.4. Разделы в объявлениях классов необходимо отделять одной или несколькими пустыми строками.

 

ПОЧЕМУ. Пустые строки между разделами облегчают ориентирование в объявлении класса.

4.2. Пробелы

4.2.1. Основные правила употребления пробелов

- Операторы следует разделять пробелами;

- После зарезервированных ключевых слов языка C++ следует ставить пробел;

- После запятых следует ставить пробелы;

- Двоеточия следует отделять пробелами;

- После точек с запятой в цикле for следует ставить пробелы.

Хорошо

Плохо

a = (b + c) * d;

a=(b+c)*d;

while (true) {

while(true){

doSomething(a, b, c, d);

doSomething(a,b,c,d);

for (i = 0; i < 10; i++) {}

for(i=0;i<10;i++){}

 

ПОЧЕМУ. Выделяет отдельные части выражений. Улучшает читаемость.

Исключением является конструкция

case <constant>:

в которой константа не отделяется от двоеточия пробелом.

 

4.2.2. После имён методов нельзя ставить пробел.

Хорошо

doSomething(currentFile);

 

ПОЧЕМУ. Улучшает читаемость.

 

4.2.3. Логические блоки в коде следует отделять пустой строкой.

 

 

 

Хорошо

Matrix4x4 matrix = new Matrix4x4();

 

double cosAngle = Math.cos(angle);

double sinAngle = Math.sin(angle);

 

matrix.setElement(1, 1,  cosAngle);

matrix.setElement(1, 2,  sinAngle);

matrix.setElement(2, 1, -sinAngle);

matrix.setElement(2, 2,  cosAngle);

 

multiply(matrix);

 

ПОЧЕМУ. Улучшает читаемость.

 

4.2.4. Переменные в объявлениях можно выравнивать.

Хорошо

AsciiFile* file;

int        pointsNumber;

float      x, y;

 

ПОЧЕМУ. Улучшает читаемость. Чётче видны пары type — variable.

4.3. Оформление классов

4.3.1. В объявлениях классов разделы класса public, protected и private должны быть отсортированы. Все разделы должны быть явно указаны.

Порядок разделов:

- public;

- public slots;

- signals;

- protected (для методов);

- protected (для переменных);

- protected slots;

- private (для методов);

- private slots;

- private (для переменных).

В любом из разделов сначала определяются методы, затем переменные. Часть разделов при необходимости может не употребляться.

Хорошо

class SomeClass : public BaseClass

{

public:
...

protected:
...

private:
...

}

 

ПОЧЕМУ. Сперва должен идти раздел public, что избавит желающих ознакомиться с классом от чтения разделов protected/private.

 

4.3.2. В исходном файле реализации класса в первую очередь должна приводиться реализация конструктора класса вне зависимости от его принадлежности к public/protected/private (при наличии пользовательского конструктора), затем деструктора класса (при наличии пользовательского деструктора).

 

ПОЧЕМУ. Улучшает читаемость кода.

 

4.3.3. Реализации методов классов должны быть сгруппированы по правам доступа к данным методам. Группы методов по правам доступа должны идти в том же порядке, что и разделы в объявлении класса. Каждая группа методов должна быть помечена комментарием с названием соответствующего раздела, напр., PUBLIC, PRIVATE SLOTS и т.д. Длина строки разделителя должна составлять 70 символов.

Хорошо

/* ***************************

 * PUBLIC

 * ***************************

*/

 

/* ***************************

 * PRIVATE SLOTS

 * ***************************

*/

 

ПОЧЕМУ. Упорядочивает реализации методов класса, упрощает поиск реализации необходимого метода.

 

4.3.4. В определении класса и соответствующем исходном файле методы чтения и записи атрибутов класса должны быть помечены соответствующими комментариями //GETTERS и //SETTERS.

 

ПОЧЕМУ. Улучшает читаемость кода.

 

4.3.5. Реализации методов в исходном файле должны идти в той же последовательности, что и объявление данных методов в объявлении класса.

 

ПОЧЕМУ. Упрощает поиск реализации методов.

4.4. Оформление составных операторов

4.4.1. Конструкцию if-else следует оформлять следующим образом:

Хорошо

Плохо

if (condition) {
statements;

}

else {
statements;

}

if (condition) {
statements;

}

else if (condition) {
statements;

}

else {
statements;

}

if (condition) {
statements;

} else {
statements;

}

if (condition)

{
statements;

}

else

{
statements;

}

if (condition)

{
statements;

}

else if (condition)

{
statements;

}

else

{
statements;

}

if (condition)

{
statements;

} else

{
statements;

}

 

ПОЧЕМУ. Необходимо каждую часть if-else помещать на отдельной строке. Это упрощает действия с кодом, например, перемещение блока else.

 

4.4.2. Цикл for следует оформлять следующим образом:

 

 

 

Хорошо

for (initialization;
 condition; update) {
 statements;

}

for (initialization;
 condition; update)

{
 statements;

}

 

 

4.4.3. Цикл while следует оформлять следующим образом:

Хорошо

while (condition) {
    statements;

}

while (condition)

{
    statements;

}

 

 

4.4.4. Конструкцию switch следует оформлять следующим образом:

Хорошо

switch (condition) {

case ABC:

    statements;

    // Отсутствует

    //"break"

case DEF:

    statements;

    break;

default:

    statements;

    break;

}

switch (condition)

{

case ABC:

    statements;

    // Отсутствует

    //"break"

case DEF:

    statements;

    break;

default:

    statements;

    break;

}

 

ПОЧЕМУ. Служебное слово case имеет отступ относительно всей конструкции, что помогает её выделить. Если где-то отсутствует ключевое слово break, то предупреждением об этом должен служить комментарий. Программисты часто забывают ставить это слово, поэтому случай нарочного его пропуска должен описываться специально директивой fallthrough.

 

4.4.5. Конструкцию try-catch следует оформлять следующим образом:

Хорошо

try {
statements;

}

catch (Exception& exception) {
statements;

}

try

{
statements;

}

catch (Exception& exception)

{
statements;

}

 

ПОЧЕМУ. Вопросы, касающиеся закрывающих фигурных скобок у конструкции if-else, применимы и здесь.

 

4.4.6. Фигурные скобки нельзя опускать, даже если составной оператор либо метод содержит только одно выражение в теле.

 

 

Хорошо

for (initialization;
condition; update)

{
statements;

}

for (initialization;
condition; update){
statements;

}

while (condition)

{
statement;

}

while (condition){
statement;

}

if (condition)

{
statement;

}

if (condition) {
statement;

}

4.5. Комментарии

4.5.1. Сложный код, написанный с использованием хитрых ходов, следует не комментировать, а переписывать!

 

ПОЧЕМУ. Следует делать как можно меньше комментариев, делая код самодокументируемым путём выбора правильных имён и создания ясной логической структуры.

 

4.5.2. Поясняющие комментарии следует писать на английском, комментарии, предназначенные для формирования документации, можно писать на русском.

 

ПОЧЕМУ. В интернациональной среде английский — предпочтительный язык.

 

4.5.3. Используйте // для поясняющих комментариев, включая многострочные.

Хорошо

// Комментарий, расположенный

// на нескольких строках.

 

Если следовать этой рекомендации, многострочные комментарии /* */ можно использовать для отладки и иных целей.

 

4.5.4. Используйте /**  */ для комментариев, предназначенных для формирования документации.

Хорошо

/**
Функция без параметров,
возвращает всегда true.

/*
